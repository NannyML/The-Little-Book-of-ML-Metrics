\chapteropener{Ranking}{corallight}{coralaccent}{%
Search results, recommendations and retrieved documents are lists, and a list is right or wrong by position: the same relevant item at
rank $1$ and at rank $10$ is a different outcome. The metrics here cut the list at some depth $K$ and weight what they find by where it
sits. Precision and recall at $K$ count; MRR and MAP reward early hits; CG sums graded relevance and DCG and nDCG discount it by
position; hit rate asks only whether anything relevant made the cut, and FCP scores the order of every pair. A second group (coverage,
diversity, novelty, serendipity) scores the catalog rather than the query, because a recommender that is accurate and shows everyone
the same ten items is failing at something these metrics name.}{In this chapter}

% ---------- @K Metrics ----------
\clearpage
\thispagestyle{rankingstyle}
\section{@K Metrics}\label{sec:k-metrics}
\subsection{@K Metrics}

Most ranking metrics score the full ordering, but users rarely scroll past the first screen. The @K family restricts evaluation to the top-$K$ items, matching the slice of the ranking that actually drives engagement. Any base metric — Precision, Recall, MRR, MAP, nDCG — has an @K variant that ignores everything below rank $K$.

\begin{center}
    $\displaystyle Precision@K = \frac{|\text{relevant items in top-}K|}{K}$
\end{center}

The value of $K$ is set by the product, not the model: $K = 5$ for a mobile carousel, $K = 10$ for a search results page. Two models with identical full-ranking scores can disagree completely at small $K$, so the cutoff is part of the evaluation.

\textbf{When to use @K Metrics?}

Use @K when the user sees a fixed window: search pages, feeds, carousels. Pick $K$ from the UI surface. Avoid @K when the full ordering matters downstream (re-ranking, audit) or when $K$ is itself the variable being optimized.

\coloredboxes{
    \item Matches what users actually see. $Precision@5$ on a mobile carousel directly measures the relevance of the slice the user is shown.
    \item Composable across metrics. Every base ranking metric has a clean @K variant, so a single cutoff applies across an evaluation suite.
}
{
    \item Sensitive to the choice of $K$. Precision@$5$ and Precision@$20$ can order models differently; report at several $K$ or fix $K$ from the product spec.
    \item Hard cutoff at rank $K$. An item at rank $K+1$ is treated identically to one at rank $1000$, even though it nearly made the list.
    \item Precision@$K$ has a ceiling when relevant items are scarce. With three relevant items, $Precision@10$ maxes at $0.3$ even for a perfect ranker.
}

\clearpage
\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/at_K_precision_recall.png}
\end{figure*}

\textbf{Figure. @K Metrics.} Precision@$K$ (blue) falls and Recall@$K$ (red) rises as $K$ grows — the universal trade-off. Precision@$K$ starts high (the top of the list is usually right) and decays as you scoop up more borderline items; Recall@$K$ rises monotonically because more items can only retrieve more of the relevant set. The two curves cross exactly at $K =$ (total relevant items) by construction — $20$ in this example — which is why the crossover itself is not a useful operating point, only the shapes are.

\orangebox{Did you know that...}
{The choice of $K$ is often driven by UI constraints. If a mobile app shows five cards on screen, $Precision@5$ measures exactly the value of that screen. Reporting $Precision@10$ when only five are visible measures a different product than the one users see.}

\textbf{Other related metrics}

Common @K variants include Precision@$K$, Recall@$K$, MAP@$K$, and nDCG@$K$. For a binary check of whether any relevant item appears in the top-$K$, see Hit Rate.

% ---------- Mean Reciprocal Rank ----------
\clearpage
\thispagestyle{rankingstyle}
\section{MRR}\label{sec:mrr}
\subsection{Mean Reciprocal Rank}

MRR scores a system on a narrow question: how high in the list is the first relevant result? Average that reciprocal across all queries and the result is MRR. The metric heavily weights the rank-$1$ result and gives little credit when the first relevant item appears at rank $5$ or $10$ — useful for tasks where users abandon the list after the first miss.

\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                MRR = \frac{1}{{\color{nmlred}|Q|}} \sum_{i=1}^{|Q|} \frac{1}{{\color{nmlcyan}rank_i}}
                $
            }
        };
        \path[room for labels] ([yshift=0.00cm]a.north) ([yshift=-0.07cm]a.south);
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(-0.11,0.23)$) to[bend left=15] node[pos=1, left] {number of queries} +(-1.00,-0.30);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.south)+(1.80,0.28)$) to[bend right=15] node[pos=1, right] {first relevant rank} +(1.00,-0.30);
    }
\end{center}

MRR lives in $[0, 1]$. A score of $1$ means the relevant item sits at rank $1$ for every query; $0.5$ means the average first-hit is at rank $2$. The decay is hyperbolic — rank $5$ scores $0.2$, rank $20$ scores $0.05$ — so anything past the first relevant item is essentially invisible.

\textbf{When to use MRR?}

Use MRR for known-item search and Q\&A: each query has one canonical answer and the task is to surface it first (``what's the capital of Belgium?''). Avoid MRR when queries have multiple relevant items of comparable value (movies, news) — MRR scores the same whether the slots after the first hit are gold or junk.

\coloredboxes{
    \item Mirrors known-item search. Users want the answer at rank $1$, and MRR penalizes anything below it.
    \item Bounded in $[0, 1]$ and averageable across queries with no normalization.
}
{
    \item Ignores items below the first hit. $[\textit{relevant, junk, junk}]$ and $[\textit{relevant, gold, gold}]$ score the same.
    \item Steep penalty for top-of-list misses. Rank $1$ to rank $2$ halves the score; rank $1$ to rank $10$ drops it by $90\%$.
    \item Inflatable with short rankings — pair MRR with Recall or coverage.
}

\clearpage

\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=0.95\textwidth]{figures/MRR_ranked_lists.png}
\end{figure*}

\textbf{Figure. MRR.} Six example queries, one per row. The filled cyan dot marks each query's first relevant item — the only one MRR scores. Open circles are additional relevant items that the metric ignores; small gray dots are irrelevant. The per-query reciprocal rank sits on the right; MRR averages them at the bottom. Q1 (relevant at rank $1$) and Q5 (rank $10$) differ by $10\times$ in score; Q6 (no relevant item in the top-$10$) contributes zero.

\orangebox{Did you know that...}
{MRR is the default scorer for question-answering benchmarks like TREC-QA and Natural Questions because the task is structurally known-item: there is one right answer and the user wants it first. Swapping MRR for nDCG only changes the score on queries with multiple plausible answers — for single-answer queries the two are essentially equivalent.}

\textbf{Other related metrics}

For multi-relevant evaluation use MAP. For graded relevance (some items more relevant than others, e.g., a five-star rating system) use nDCG — it credits every relevant item with a position-discounted contribution, whereas MRR collapses the entire list to a single number from the first hit. For a binary top-$K$ check use Hit Rate.


% ---------- Mean Average Precision ----------
\clearpage
\thispagestyle{rankingstyle}
\section{MAP}\label{sec:map}
\subsection{Mean Average Precision}

MAP rewards rankers for placing relevant items high in the list. For each query, walk down the ranking and average the precision at every position where a relevant item appears — that is the Average Precision (AP). MAP is the mean of AP across queries. A relevant item at rank $1$ contributes precision $1.0$; at rank $10$ it contributes $0.1$, so MAP collapses when relevant items are buried.

\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                MAP = \frac{1}{{\color{nmlred}|Q|}} \sum_{q=1}^{|Q|} \frac{1}{|{\color{nmlcyan}R_q}|} \sum_{k=1}^{n} {\color{nmlpurple}P(k)} \cdot {\color{nmlcyan}rel(k)}
                $
            }
        };
        \path[room for labels] ([yshift=0.30cm]a.north) ([yshift=-0.00cm]a.south);
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(-1.74,0.30)$) to[bend left=15] node[pos=1, left] {number of queries} +(-1.00,-0.30);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(3.46,-0.66)$) to node[pos=1, above] {relevant items} +(0.00,0.30);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.north)+(1.87,-0.66)$) to[bend right=15] node[pos=1, left] {precision at $k$} +(-1.00,0.94);
    }
\end{center}

MAP lives in $[0, 1]$. A perfect ranking — every relevant item ahead of every irrelevant one — scores $1$. The gap between MAP and the prevalence baseline (relevant items / list length) measures how much ordering work the model adds on top of plain retrieval.

\textbf{When to use MAP?}

Use MAP when relevance is binary, the full ranked list matters, and you want one number for precision plus order. It is the standard for binary-judgment IR benchmarks. Avoid MAP for graded relevance (use nDCG) or top-only evaluation (use MRR or Precision@$K$) — averaging across all positions lets a strong tail mask a weak top.

\enlargethispage{2\baselineskip}
\coloredboxes{
    \item Captures precision and rank order in one number. A model that surfaces relevant items earlier always scores higher.
    \item Averages cleanly across queries with different numbers of relevant items — AP is already per-query normalized.
}
{
    \item Assumes binary relevance. No way to say ``item A is more relevant than item B'' the way nDCG can.
    \item Requires complete labels. If a query has five relevant items and only three are labeled, AP is biased downward.
    \item Hard to translate to a user-facing story. ``MAP $= 0.42$'' lands flat next to ``$Precision@10 = 0.6$''.
}

\clearpage
\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=\textwidth]{figures/MAP_precision_strips.png}
\end{figure*}

\textbf{Figure. MAP.} Two rankings with the same four relevant items. The number under each filled dot is the running precision at that rank: $1/1 = 1.00$ for the first relevant item at rank $1$, $4/6 = 0.67$ for the fourth relevant item landing at rank $6$. AP is exactly the mean of those numbers; a single position shift reshuffles the whole sum. Same recall, very different AP.

\orangebox{Did you know that...}
{MAP became the default scorer for the TREC (Text REtrieval Conference) evaluations, which have been benchmarking information retrieval systems since 1992. The choice was deliberate: MAP credits precision at every position where a relevant item appears, so a system that surfaces the same items earlier always wins — exactly the property TREC wanted to reward across thirty years of system comparisons.}

\textbf{Other related metrics}

For graded relevance use nDCG. For top-only evaluation use MRR or Precision@$K$. AP and MAP are related as point and average: AP is the per-query score, MAP is the mean across queries.

% ---------- Hit Rate ----------
\clearpage
\thispagestyle{rankingstyle}
\section{Hit Rate}\label{sec:hit-rate}
\subsection{Hit Rate}

Hit Rate answers a yes-no question per user: did the top-$K$ list contain at least one relevant item? Average that indicator across users and you have the Hit Rate of the system. It ignores how many relevant items appeared and where they were — only whether the user got something or nothing.

\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                Hit\ Rate = \frac{1}{{\color{nmlred}|U|}} \sum_{u=1}^{|U|} {\color{nmlgreen}\mathds{1}}\left(|{\color{nmlcyan}R_u} \cap {\color{nmlpurple}Top\text{-}K_u}| > 0\right)
                $
            }
        };
        \path[room for labels] ([yshift=0.00cm]a.north) ([yshift=-0.55cm]a.south);
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(-1.59,0.22)$) to[bend left=15] node[pos=1, left] {number of users} +(-1.00,-0.39);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.south)+(0.69,0.61)$) to[bend left=15] node[pos=1, left] {relevant items} +(-1.00,-1.20);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.south)+(2.94,0.61)$) to node[pos=1, below] {top-K items} +(0.00,-0.31);
    }
\end{center}

A Hit Rate of $0.72$ means $72\%$ of users got at least one relevant item in their top-$K$ list; the other $28\%$ saw nothing useful. The low bar makes Hit Rate the right metric for catching a specific failure: lists that look diverse but happen to miss every user's actual interests.

\textbf{When to use Hit Rate?}

Use Hit Rate as a floor for top-$K$ quality: ``what fraction of sessions show at least one relevant item?'' translates directly to product metrics. Avoid Hit Rate as the primary optimization target — a model can score well by recommending broadly, with no signal about whether the hit is buried in junk.

\coloredboxes{
    \item Easy to communicate. ``$72\%$ of sessions see at least one relevant item'' maps directly onto product metrics like activation or session quality.
    \item Robust to sparsity and missing labels. A single relevant item per user is enough to score.
    \item Endpoint-interpretable. $0$ means total failure; $1$ means every user is served.
}
{
    \item Position-blind. A relevant item at rank $1$ scores the same as one at rank $K$.
    \item Count-blind. A list with one relevant item scores the same as a list with five.
    \item Saturates fast. At small $K$ the metric undercounts; at large $K$ it pins to $1$. Pick $K$ where Hit Rate still moves between models.
}

\clearpage
\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=0.6\textwidth]{figures/Hit_Rate_vs_K.png}
\end{figure*}

\textbf{Figure. Hit Rate.} Hit Rate climbs with $K$: at $K = 1$ only $15\%$ of users see a relevant item in the first slot; at $K = 50$ that rises to $96\%$. The curve flattens as $K$ grows because the remaining failures are users with no relevant items anywhere in the top-$50$ — stretching $K$ further does not help that segment.

\orangebox{Did you know that...}
{Recommender systems papers often call Hit Rate ``Recall@$K$'' and use the two interchangeably. They are the same metric only when each user has exactly one relevant item — the typical leave-one-out evaluation setup. With multiple relevant items per user, Recall@$K$ measures the fraction retrieved, while Hit Rate stays binary. The naming clash trips up cross-paper comparisons more often than you would expect.}

\textbf{Other related metrics}

For position-aware evaluation use MRR or nDCG. For counting how many relevant items the list retrieved, use Recall@$K$. Hit Rate is the binary collapse of Recall@$K$.

% ---------- Cumulative Gain ----------
\clearpage
\thispagestyle{rankingstyle}
\section{CG}\label{sec:cg}
\subsection{Cumulative Gain}

Cumulative Gain (CG) sums the relevance scores of the items in a recommendation list. With graded relevance — $3$ for ``perfect'', $1$ for ``marginal'', $0$ for ``irrelevant'' — $CG_K$ is the total relevance packed into the top-$K$. The catch is that CG ignores rank: a relevant item at position $1$ adds the same as one at position $K$.

\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                CG_p = \sum_{i=1}^{{\color{nmlred}p}} {\color{nmlcyan}rel_i}
                $
            }
        };
        \draw[overlay,-latex,nmlred, semithick] ($(a.north)+(0.40,-0.07)$) to[bend right=15] node[pos=1, left] {number of items} +(-1.00,0.30);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(1.23,-0.54)$) to[bend left=15] node[pos=1, right] {relevance of item $i$} +(1.00,0.30);
    }
\end{center}

CG is unbounded and order-invariant: two lists with the same items in different orders have identical CG. That makes it useful as a baseline number — ``how much total relevance did we retrieve?'' — but not as a standalone ranking metric. DCG and nDCG (next pages) fix the rank-insensitivity by discounting later positions.

\textbf{When to use CG?}

Use CG when only total retrieved relevance matters and ordering is decided downstream (a re-ranker reshuffles the list, or items are shown simultaneously). Avoid CG when position matters to the user — which covers most ranking applications. Use DCG or nDCG instead.

\coloredboxes{
    \item Simplest relevance aggregation possible: add up the scores. Trivial to compute and explain.
    \item Works with graded relevance out of the box, unlike Hit Rate or binary $Precision@K$.
}
{
    \item Order-invariant. A list with the best item at rank $1$ scores the same as one with the best item at rank $K$.
    \item Not normalized. $CG = 12$ vs $CG = 6$ across queries says nothing about which ranking was better.
    \item Falls back to a raw count of relevant items when only binary labels are available.
}

\clearpage
\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=\textwidth]{figures/CG_order_blind.png}
\end{figure*}

\textbf{Figure. CG.} The same ten items in two orders, best first and best last. CG adds the relevance grades and reaches $12$ either
way: it cannot tell the two lists apart. DCG discounts each grade by $1/\log_2(i+1)$ and scores them $7.28$ and $4.38$. CG is a check on
how much relevance a list retrieved, not on where it put it.

\orangebox{Did you know that...}
{The order-invariance of CG is its entire design flaw: swap any two items and the score is unchanged, which makes CG useless for ranking. The metric still gets used in retrieval-then-rerank pipelines, where the retrieval stage scores raw recall and a downstream model handles the ordering. Outside that pattern, CG on its own in a results table is a red flag.}

\textbf{Other related metrics}

DCG extends CG by discounting later positions. nDCG normalizes DCG against the ideal ranking, so scores are comparable across queries with different relevance budgets. In practice, CG is the warm-up step toward those two.

% ---------- Discounted Cumulative Gain ----------
\clearpage
\thispagestyle{rankingstyle}
\section{DCG}\label{sec:dcg}
\subsection{Discounted Cumulative Gain}

DCG fixes the order-blindness of CG by discounting items further down the list. The position discount $1/\log_2(i + 1)$ is heaviest at rank $1$ (no discount) and decays slowly: rank $2$ gets a factor of $0.63$, rank $10$ gets $0.29$, rank $100$ gets $0.15$. DCG rewards relevance but heavily favors relevance that appears early.

\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                DCG_p = \sum_{i=1}^{{\color{nmlred}p}} \frac{{\color{nmlcyan}rel_i}}{{\color{nmlpurple}\log_2(i + 1)}}
                $
            }
        };
        \path[room for labels] ([yshift=0.09cm]a.north) ([yshift=-0.28cm]a.south);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(1.45,-0.19)$) to[bend right=15] node[pos=1, left] {relevance of item $i$} +(-1.00,0.30);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.south)+(1.85,0.31)$) to[bend left=15] node[pos=1, left] {position discount} +(-1.00,-0.61);
    }
\end{center}

The logarithmic discount is gentle compared to MRR's $1/rank$ — DCG still credits items at rank $20$ or $50$, just less. So DCG sees the whole list, with diminishing weight, where MRR effectively only sees the top.

\textbf{When to use DCG?}

Use DCG when relevance is graded (a five-star rating, a three-tier label) and the full ranked list matters. The discount $1/\log_2(i+1)$ models attention decay smoothly. Avoid DCG when you need cross-query comparison — scores depend on each query's relevance budget, so $DCG = 7$ for one and $DCG = 4$ for another is not interpretable without normalization. That is what nDCG is for.

\coloredboxes{
    \item Rewards both relevance and ordering. Position $1$ gets full weight; position $K$ gets $1/\log_2(K+1)$, slow enough that the tail still counts.
    \item Works directly with graded relevance, unlike MAP or Hit Rate which need binary judgments.
}
{
    \item Unbounded and not normalized. $DCG = 7$ vs $DCG = 4$ across queries means nothing on its own.
    \item Discount base is a free parameter. Most implementations use $\log_2$; others use $\log_e$ or $\log_{10}$, so library outputs may not be directly comparable.
}

\clearpage
\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=0.8\textwidth]{figures/CG_vs_DCG.png}
\end{figure*}

\textbf{Figure. DCG.} The same ranked list scored by CG (red) and DCG (blue). Both agree at rank $1$, then diverge: DCG applies a $1/\log_2(i+1)$ discount at every subsequent position, CG does not. The shaded area is how much relevance DCG throws away relative to CG by accounting for position. At $K = 10$ the final scores are $CG = 12.0$ and $DCG = 7.16$ — same items, $40\%$ of the total relevance discounted as ``too far down the list''.

\orangebox{Did you know that...}
{The logarithmic discount in DCG was introduced by J\"{a}rvelin and Kek\"{a}l\"{a}inen in 2002. The choice of $\log_2$ is conventional but arbitrary — some implementations use natural log or $\log_{10}$, and scores across libraries are not directly comparable unless the base is the same.}

\textbf{Other related metrics}

For cross-query comparison use nDCG, which divides DCG by the ideal ranking's DCG. For binary relevance, MAP is simpler and avoids the discount-base ambiguity. For top-only evaluation, MRR.

% ---------- Normalized Discounted Cumulative Gain ----------
\clearpage
\thispagestyle{rankingstyle}
\section{nDCG}\label{sec:ndcg}
\subsection{Normalized Discounted Cumulative Gain}

nDCG divides DCG by the best possible DCG for the same items (the Ideal DCG, or IDCG). The ratio is bounded in $[0, 1]$: $1$ means the model produced the ideal ordering, $0$ means every relevant item was sorted to the bottom. Because each query is scored against its own ideal, nDCG values from queries with very different relevance budgets are directly comparable.

\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                nDCG_p = \frac{{\color{nmlcyan}DCG_p}}{{\color{nmlpurple}IDCG_p}}
                $
            }
        };
        \path[room for labels] ([yshift=0.25cm]a.north) ([yshift=-0.19cm]a.south);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(1.11,-0.01)$) to[bend right=15] node[pos=1, left] {actual DCG} +(-1.00,0.30);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.south)+(1.10,0.06)$) to[bend left=15] node[pos=1, left] {ideal DCG} +(-1.00,-0.30);
    }
\end{center}

IDCG is the DCG of the optimally sorted list (relevant items first, in descending relevance). An $nDCG = 0.85$ means the model achieved $85\%$ of the maximum possible discounted relevance for that query — a directly readable number, unlike raw DCG.

\textbf{When to use nDCG?}

Use nDCG when relevance is graded and you need a single comparable number across queries with different relevance budgets. It is the de facto offline metric for graded-relevance ranking. Avoid nDCG when relevance is purely binary (use MAP — same idea, less machinery) or when only the very top of the list matters (use MRR or Precision@$K$).

\coloredboxes{
    \item Bounded in $[0, 1]$ and comparable across queries — fixes DCG's main weakness.
    \item Handles graded relevance natively. A five-star rating gives a richer signal than ``relevant/not'', and nDCG uses it directly.
}
{
    \item Requires labeled relevance scores. With missing or noisy labels, IDCG is wrong and nDCG inherits the error.
    \item Sensitive to the truncation $K$ in $nDCG_K$. Truncating at $K = 5$ vs $K = 100$ gives very different scores; report at the $K$ that matches the product.
}

\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/nDCG_degradation.png}
\end{figure*}

\textbf{Figure. nDCG.} Apply random pair-swaps to a perfectly ranked list and recompute nDCG after each. The descent is noisy: most swaps barely move the score (the long plateau near $1.0$, then again near $0.7$), but a single swap that demotes a rank-$1$ item drops nDCG sharply (the cliff around swap $7$). A spike at swap $16$ shows a swap that put a high-relevance item back to the top. The shape — noisy plateau with rare cliffs — is what generalizes; nDCG mostly tracks where the few most-relevant items sit.

\orangebox{Did you know that...}
{nDCG is the standard offline evaluation metric at most major tech companies for search and recommendation systems. It is also the primary metric used in the annual TREC Web Track and in Kaggle recommendation competitions — when a search or recsys leaderboard reports one number, it is almost always nDCG.}

\textbf{Other related metrics}

nDCG is DCG normalized against the ideal ranking. For binary relevance use MAP — simpler and less label-hungry. For known-item search use MRR. For top-only evaluation in product-anchored settings, Precision@$K$.

% ---------- Fraction of Concordant Pairs ----------
\clearpage
\thispagestyle{rankingstyle}
\section{FCP}\label{sec:fcp}
\subsection{Fraction of Concordant Pairs}

FCP turns ranking into a pairwise question: for every pair of items where the user prefers one over the other, did the model rank them in the right order? The metric is the fraction of such pairs that came out concordant. A coin-flip ranker scores $0.5$; a perfect ranker scores $1$.

\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                FCP = \frac{|{\color{nmlcyan}\text{concordant pairs}}|}{|{\color{nmlpurple}\text{comparable pairs}}|}
                $
            }
        };
        \path[room for labels] ([yshift=0.27cm]a.north) ([yshift=-0.22cm]a.south);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(0.31,-0.04)$) to[bend right=15] node[pos=1, left] {correctly ordered pairs} +(-1.00,0.30);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.south)+(0.31,0.07)$) to[bend left=15] node[pos=1, left] {total comparable pairs} +(-1.00,-0.30);
    }
\end{center}

A comparable pair is one where the ground truth says which item the user prefers. FCP is undefined for pairs the user has no opinion on — a fact that becomes important in sparse implicit-feedback data, where most pairs are unobserved.

\textbf{When to use FCP?}

Use FCP when relevance is expressed as pairwise preferences rather than absolute scores: ``the user clicked A but not B'', ``finished show X, bailed on Y''. It is the natural metric for learning-to-rank models trained with pairwise losses. Avoid FCP when you have rich graded relevance — collapsing a five-star rating to a binary preference throws away signal that nDCG would use.

\coloredboxes{
    \item Captures relative ranking quality directly, matching how recommender models are usually trained (pairwise losses).
    \item Robust to absolute-score noise. If user A rates everything $3$ and user B rates everything $5$, FCP recovers each user's preference order; nDCG would see different score ranges.
}
{
    \item Quadratic in list size. Ranking $1{,}000$ items means $\sim 500{,}000$ pairs per user — expensive at scale.
    \item Treats all pairs equally. A swap between rank $1$ and rank $2$ counts the same as a swap between rank $500$ and rank $501$.
}

\clearpage
\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=\textwidth]{figures/FCP_comparison.png}
\end{figure*}

\textbf{Figure. FCP.} Predicted rank vs true preference rank for the same five items, scored by two rankers. The dashed line is perfect agreement. \underline{Left:} a good ranking ($FCP = 0.90$) — four of five items sit on the diagonal, the only inversion is the swap between items $2$ and $3$. Right: a near-reversed ranking ($FCP = 0.30$) — most items land far from the diagonal. FCP counts the fraction of point-pairs whose relative order matches the diagonal's slope.

\orangebox{Did you know that...}
{FCP is closely related to Kendall's tau rank correlation coefficient. Both measure pairwise agreement in rankings, but FCP is expressed as a proportion in $[0, 1]$ while Kendall's tau is rescaled to $[-1, 1]$. The relationship: $\tau = 2 \cdot FCP - 1$.}

\textbf{Other related metrics}

FCP is structurally Kendall's tau without the rescaling. For position-weighted evaluation use nDCG. For top-only evaluation use MRR or Precision@$K$. For binary-relevance ranking, MAP.

% ---------- Diversity ----------
\clearpage
\thispagestyle{rankingstyle}
\section{Diversity}\label{sec:diversity}
\subsection{Diversity}

Diversity scores a recommendation list by how dissimilar its items are from each other on average. Sum the pairwise dissimilarities $d(i, j)$ across all unordered pairs and divide by the number of pairs. A list of ten action movies scores low; a list mixing action, comedy, and documentary scores high.

\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                Diversity = \frac{1}{{\color{nmlred}|L|(|L|-1)}} \sum_{i \in L} \sum_{j \in L, j \neq i} {\color{nmlcyan}d(i, j)}
                $
            }
        };
        \path[room for labels] ([yshift=0.30cm]a.north) ([yshift=-0.00cm]a.south);
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(-0.90,0.31)$) to[bend left=15] node[pos=1, left] {list size} +(-1.00,-0.30);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(3.51,-0.34)$) to[bend right=15] node[pos=1, left] {pairwise dissimilarity} +(-1.00,0.62);
    }
\end{center}

The choice of $d(i, j)$ drives everything. Common options: $1 - \cos(e_i, e_j)$ when item embeddings $e$ are available, or category distance ($0$ same genre, $1$ different) when only labels are. The metric inherits whatever bias the embedding has, so a model evaluated on cosine diversity can rank very differently under category diversity.

\textbf{When to use Diversity?}

Use Diversity as a guardrail alongside accuracy: an nDCG-optimal recommender often produces ten near-identical items, and the diversity score will flag that. It also fits products where exploration is the explicit value — onboarding feeds, ``something new'' surfaces. Avoid Diversity as the primary objective — maximizing it alone produces random recommendations.

\coloredboxes{
    \item Catches a real failure that accuracy metrics miss: the ``ten of the same'' problem in collaborative filtering.
    \item Composable. Mix Diversity with nDCG or MAP to define a trade-off curve and pick a model on the Pareto front.
}
{
    \item Entirely defined by $d(i, j)$. Switching from category-based to embedding-based dissimilarity can flip the ranking of models.
    \item Trade-off with relevance. Pushing Diversity up usually pushes nDCG down; the optimal point is product-dependent.
}

\clearpage
\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=\textwidth]{figures/Diversity_comparison.png}
\end{figure*}

\textbf{Figure. Diversity.} Two six-item recommendation lists rendered as horizontal strips, each tile colored by genre. \underline{Top:} one item per genre — Intra-List Diversity hits its maximum ($ILD = 1.00$) because every pair of items disagrees on category. Bottom: six action items — every pair matches, so $ILD = 0.00$. The metric reads the visible color mix of the list, not its accuracy.

\orangebox{Did you know that...}
{Intra-List Diversity (ILD) is the most common formulation of diversity in recommender systems. The choice of dissimilarity function $d(i,j)$ is crucial — common options include $1 - \cos$ of item feature vectors, or genre/category distance. Two papers can both report ``ILD'' and rank models differently because the underlying $d$ is different.}

\textbf{Other related metrics}

Diversity captures how different items are from each other; Novelty captures how unfamiliar they are to the user; Serendipity combines relevance with unexpectedness. Coverage measures catalog utilization across all users — a system-level metric that is orthogonal to per-list diversity.

% ---------- Novelty ----------
\clearpage
\thispagestyle{rankingstyle}
\section{Novelty}\label{sec:novelty}
\subsection{Novelty}

Novelty scores how unfamiliar the recommended items are. The simplest formulation inverts item popularity: items few users have seen score high, mainstream items score low. The information-theoretic version $-\log_2 P(i)$ measures the same thing in bits — a popular item with $P = 0.5$ has $1$ bit of novelty; a rare item with $P = 0.01$ has $6.6$ bits.

\begin{center}
    \[
        Novelty(i) = -\log_2 P(i)
    \]
\end{center}

Other formulations in the literature ($1 - P(i)$, population-conditional variants) rank items the same way; they differ only in scale. Aggregating across a list usually means averaging the per-item scores.

\textbf{When to use Novelty?}

Use Novelty in products where ``something new'' is the explicit value proposition: discovery feeds, onboarding for new users, content rabbit holes. Pair it with an accuracy metric — a recommender that only shows novel items is just a popularity-inverter. Avoid Novelty in search-style products: users typing a query rarely want unfamiliar results.

\coloredboxes{
    \item Mitigates the popularity bias of collaborative filtering, which otherwise drowns the long tail.
    \item Cheap to compute — just popularity counts, no per-user state.
}
{
    \item Penalizes popular items even when popular is correct. A hit pop song has high $P(\text{seen})$ and low Novelty.
    \item Per-item, not per-list. A list of ten different rare items scores high even if they all sit in the same niche.
}


\clearpage
\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=0.6\textwidth]{figures/Novelty_curve.png}
\end{figure*}

\textbf{Figure. Novelty.} Novelty as $-\log_2 P(i)$ over item popularity. Two reference points: a rare item ($P = 0.01$) scores $6.6$ bits; a mainstream one ($P = 0.5$) scores $1$ bit. The curve is steep near $P = 0$ — the long tail spans most of the bits — and flat past $P = 0.5$, where mainstream items all look interchangeably familiar.

\orangebox{Did you know that...}
{The self-information formulation $Novelty(i) = -\log_2 P(i)$ is borrowed from information theory. A popular item with $P(i) = 0.5$ has novelty of $1$ bit, while a rare item with $P(i) = 0.01$ has novelty of $6.6$ bits. The same machinery powers entropy and cross-entropy losses, so a Novelty-aware ranker is structurally close to a self-supervised language model in how it weights rare events.}

\textbf{Other related metrics}

Novelty is per-item popularity-based; Diversity is per-list pairwise dissimilarity; Serendipity adds relevance to novelty (an item is serendipitous only if it is both novel AND relevant). For catalog-level reach, Coverage.

% ---------- Serendipity ----------
\clearpage
\thispagestyle{rankingstyle}
\section{Serendipity}\label{sec:serendipity}
\subsection{Serendipity}

Serendipity scores recommendations on two axes: relevance and unexpectedness. An item is serendipitous only if the user would have valued it AND would not have found it alone. A purely accurate recommender hits relevance but scores low on unexpectedness; a purely novel one hits the second axis but tanks the first.

\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                Serendipity = \frac{1}{{\color{nmlred}N}} \sum_{i=1}^{N} {\color{nmlcyan}rel(i)} \cdot {\color{nmlpurple}unexp(i)}
                $
            }
        };
        \path[room for labels] ([yshift=0.15cm]a.north) ([yshift=-0.18cm]a.south);
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(-0.53,0.34)$) to[bend left=15] node[pos=1, left] {number of items} +(-1.00,-0.55);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(1.25,-0.60)$) to[bend right=15] node[pos=1, left] {relevance} +(-1.00,0.78);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.south)+(2.55,0.69)$) to node[pos=1, below] {unexpectedness} +(0.00,-0.39);
    }
\end{center}

Multiplying the two factors enforces a logical AND. The metric penalizes ``relevant but predictable'' (a user's favorite genre) and ``surprising but irrelevant'' (a random catalog item) alike. Both factors live in $[0, 1]$, so Serendipity does too.

\textbf{When to use Serendipity?}

Use Serendipity in products where ``introduce the user to something they would not have found alone'' is the value proposition: music discovery, content browsing, long-tail e-commerce. Avoid it in known-item retrieval (search) and any setting where you cannot agree on a definition of $unexp(i)$ — usually derived from a baseline (popularity, history) the model is supposed to beat.

\coloredboxes{
    \item Eliminates the degenerate solutions of accuracy-alone (recommend the obvious) and Novelty-alone (recommend anything rare).
    \item Matches a measurable product outcome: returning-user satisfaction with discovery surfaces.
}
{
    \item Depends on the choice of $unexp(i)$. Different baselines (popularity, content-similarity, history) give different Serendipity scores for the same model.
    \item Hard to estimate offline — ``would the user have found this alone?'' is an interventional question; logs only show what was actually shown.
}

\clearpage
\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=0.7\textwidth]{figures/Serendipity_scatter.png}
\end{figure*}

\textbf{Figure. Serendipity.} Each point is one recommended item plotted on (relevance, unexpectedness). The shaded contours are iso-Serendipity curves $rel \cdot unexp = c$; points sitting on a darker contour score higher. The upper-right corner is the only place Serendipity lives — the other three corners all collapse to zero because one factor is small. Most accurate recommenders cluster lower-right (relevant but obvious); novelty-tuned ones cluster upper-left (surprising but irrelevant).

\orangebox{Did you know that...}
{The term serendipity comes from the 1754 fairy tale ``The Three Princes of Serendip'', whose heroes kept making fortunate discoveries by accident while looking for other things. In recommender systems the metric tries to engineer that ``happy accident'' on purpose — which is the contradiction at the core of the design.}

\textbf{Other related metrics}

Serendipity combines relevance (like Precision) with unexpectedness (a function of Novelty). For variety without relevance, Diversity. For catalog breadth, Coverage. For pure relevance, nDCG or MAP.

% ---------- Coverage ----------
\clearpage
\thispagestyle{rankingstyle}
\section{Coverage}\label{sec:coverage}
\subsection{Coverage}

Coverage is the fraction of the item catalog the recommender ever surfaces to anyone. A catalog of $10{,}000$ items where the system only ever recommends $1{,}200$ has $Coverage = 0.12$ — most of the catalog is invisible. Unlike per-list metrics, Coverage is a system-level diagnostic: it tells you whether the model is collapsing onto a small set of safe items.

\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                Coverage = \frac{|{\color{nmlcyan}\text{recommended items}}|}{|{\color{nmlpurple}\text{total catalog}}|}
                $
            }
        };
        \path[room for labels] ([yshift=0.27cm]a.north) ([yshift=-0.22cm]a.south);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(0.72,-0.04)$) to[bend right=15] node[pos=1, left] {unique recommended} +(-1.00,0.30);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.south)+(0.43,0.16)$) to[bend left=15] node[pos=1, left] {total catalog items} +(-1.00,-0.39);
    }
\end{center}

Two variants matter: simple Coverage counts items recommended at least once; weighted Coverage counts impressions per item. Simple Coverage is standard, but weighted catches the case where $90\%$ of the catalog gets recommended yet $99\%$ of impressions go to the top $5\%$ of items.

\textbf{When to use Coverage?}

Use Coverage on platforms where catalog breadth has business value: marketplaces (so sellers feel the platform serves them), media (so creators get exposure), discovery products. Track it alongside accuracy — a model with $nDCG = 0.85$ and $Coverage = 0.03$ is collapsing onto a tiny set. Avoid Coverage on platforms where only the head matters (transactional search, single-best-answer).

\enlargethispage{2\baselineskip}
\coloredboxes{
    \item System-level signal that per-list metrics miss. nDCG can be perfect while Coverage is $0.05$ — every user gets a personal top-$10$ from the same $500$ items.
    \item Cheap and label-free. Just count unique items recommended; no relevance judgments needed.
}
{
    \item Insensitive to skew. Recommending an item once versus $10{,}000$ times both count as ``covered''. Weighted Coverage fixes this but is less commonly reported.
    \item Catalog-size dependent. $Coverage = 0.5$ on $100$ items is qualitatively different from $Coverage = 0.5$ on a million. Compare within a product, not across.
}

\clearpage
\thispagestyle{customstyle}

\begin{figure*}[ht!]
    \centering
    \includegraphics[width=\textwidth]{figures/Coverage_comparison.png}
\end{figure*}

\textbf{Figure. Coverage.} Three systems shown over the same $100$-item catalog. Each square is one item; cyan if the system ever recommends it, gray if not. System A surfaces only the popular $12\%$ — most of the catalog is invisible. System B fills $48\%$. System C reaches $89\%$. Coverage is just the visible cyan fraction. The trade-off: cyan typically grows at the cost of nDCG, because items in the long tail have weaker training signal — so the goal is a Pareto point, not the maximum.

\orangebox{Did you know that...}
{Low coverage is the canonical symptom of the ``popularity bias'' problem. Collaborative-filtering models trained on engagement data tend to amplify whatever is already popular, because that is where most of the training signal lives. The fix usually involves explicit exploration (epsilon-greedy, Thompson sampling) or a popularity-debiased loss — not just adding a Coverage term to the offline metric.}

\textbf{Other related metrics}

Coverage measures system-level catalog breadth. Diversity measures within-list variety; Novelty measures per-item familiarity to one user. For accuracy, nDCG or MAP. For the unexpected-but-relevant joint, Serendipity.
