\chapteropener{Data Observability}{minthard}{mintaccent}{%
Before a model, a dashboard or a metric can be trusted, the table behind it has to arrive on time, complete, and in the shape everyone
expects. The monitors in this chapter are deliberately simple statistics: how many rows, how old, which columns, how many nulls, how
many distinct values, what the mean, the extremes and the string lengths are. What makes them useful is not the statistic but its
history: each is computed at every scan, compared with an expected range learned from earlier scans, and flagged when it leaves it
(schema changes are flagged outright). Every page shows the same table, an
orders feed monitored daily for six weeks, so the incidents one monitor catches and another misses can be read side by side. Unlike
the rest of the book, each monitor takes one page.}{In this chapter}

% ---------- Expected Range ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Expected Range}\label{sec:expected-range}
\subsection{How every monitor decides}

A row count of $2{,}600$ is not an anomaly in itself; it is one on a Wednesday that usually brings $5{,}000$. Every metric in this
chapter is a plain statistic computed on the newest partition of a table at each scan, and it becomes a monitor only when the
history of those statistics is turned into an expected range and today's value is checked against it.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \text{anomaly at } t \iff \big|\, {\color{nmlcyan}x_t} - {\color{nmlpurple}\mu_t} \,\big| > {\color{nmlyellow}z}\, {\color{nmlpurple}\sigma_t}
                $
            }
        };
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(0.2,-0.2)$) to[bend right=15] node[pos=1, left] {today's measurement} +(-1,.5);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.north)+(1.4,-0.2)$) to[bend left=15] node[pos=1, right] {baseline from history} +(0.8,.5);
        \draw[overlay,-latex,nmlyellow, semithick] ($(a.south)+(2.0,0.25)$) to[bend right=15] node[pos=1, left] {sensitivity} +(-0.8,-.5);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.south)+(2.75,0.25)$) to[bend left=15] node[pos=1, right] {spread of history} +(0.4,-.5);
    }
\end{center}

The baseline $\mu_t$ follows the metric's seasonality (in this chapter, the same weekday in earlier weeks), $\sigma_t$ is the spread of
past values around it, and $z$ sets how far outside a value must fall: $3$ by default, adjustable between $0.3$ and $6$. Feedback closes
the loop: a point marked as expected widens the range, a point marked as anomaly teaches the detector to alert on values like it.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_expected_range.png}
\end{center}

\textbf{Figure. Expected Range.} Daily row counts of an orders table. \underline{Left:} three training weeks grouped by weekday give a
mean per weekday and a pooled spread of $\sigma = 200$ rows; the range is the mean $\pm 3\sigma$. \underline{Right:} the next three weeks
checked against it. Weekends sit inside their own range although they carry $40\%$ fewer rows; a day with no load and a day whose load
stopped half-way fall outside and are flagged. Every other page in this chapter shows this table under a different monitor.

\textbf{When to use it?}

Every monitor uses it, so the question is how to set it. Keep $z = 3$ where false alarms are cheap and lower it where normal variation
is tiny (freshness, duplicates); scan at the same time every day so the baseline is stable; and partition by a column that reflects
arrival time, since a row stamped two days ago that lands today is never evaluated.

% ---------- Row Count ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Row Count}\label{sec:row-count}
\subsection{Volume}

A nightly job that loads half of yesterday's orders raises no error: the table exists, the columns are right, the rows that arrived
are valid. Only their number gives it away. Row count is the number of rows in the newest partition at scan time, the first monitor
to put on any table and the one that catches missed, partial and doubled loads.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \text{rows}_{t} = \sum_{r \in T} \mathds{1}\big[\, {\color{nmlcyan}p(r)} = {\color{nmlpurple}t} \,\big]
                $
            }
        };
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.south)+(0.9,0.3)$) to[bend left=15] node[pos=1, left] {row's partition value} +(-1,-.5);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.north)+(1.7,-0.2)$) to[bend left=15] node[pos=1, right] {the partition being scanned} +(0.6,.5);
    }
\end{center}

The partition is defined by a date or timestamp column that reflects arrival, and the count is a plain $\text{count}(*)$ over it, with
no sampling. The metadata variant, total row count and its change since the last scan, costs nothing to compute but sees the whole
table rather than the newest slice.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_row_count.png}
\end{center}

\textbf{Figure. Row Count.} The load that never ran (zero rows) and the one that stopped half-way ($2{,}600$ against a Wednesday baseline
near $5{,}000$) are flagged. The retry storm that inserted $6\%$ of one day's rows twice is not: $5{,}358$ rows, $7\%$ above the Monday
baseline, sit inside a band that reaches $11\%$ either way. Volume catches what is missing far better than what is repeated; the
Duplicates page catches that.

\textbf{When to use it?}

On every table with a regular arrival cadence: it is cheap, needs no knowledge of the content, and a missed or partial load is the most
common incident there is. Avoid trusting it alone for tables that receive late-arriving rows stamped with old dates (they never enter
the newest partition) and for tables loaded in bulk at irregular intervals, where Freshness is the better first signal.

% ---------- Freshness ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Freshness}\label{sec:freshness}
\subsection{Most Recent Timestamp}

A dashboard can be up, fast and wrong because the table behind it stopped receiving data two days ago. Freshness is the interval between
the scan time and the newest timestamp in the table's partition column: how old the latest data is at the moment someone looks.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \text{freshness}_t = {\color{nmlpurple}t_{\text{scan}}} - \max_{r \in T} {\color{nmlcyan}\text{ts}(r)}
                $
            }
        };
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.north)+(-0.2,-0.2)$) to[bend right=15] node[pos=1, left] {time of the scan} +(-1,.5);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(2.4,-0.2)$) to[bend left=15] node[pos=1, right] {newest timestamp} +(0.6,.5);
    }
\end{center}

A steady pipeline gives a steady freshness: a load that finishes at 01:30 and a scan at 06:00 read $4.5$ hours every day. The metadata
variant, last modification time, reads the same quantity from the warehouse's own bookkeeping without a query.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_freshness.png}
\end{center}

\textbf{Figure. Freshness.} Because the load lands at the same hour every night, the normal spread is minutes and the band is thin. On the
day nothing arrived the newest row is yesterday's and freshness jumps to $28.5$ hours. The partial load is caught too: the job died
$25$ minutes in, so the newest row is an hour older than usual, $5.6$ hours against $4.5$.

\textbf{When to use it?}

On every table that feeds something time-sensitive, and as the first monitor on tables that arrive in irregular bulk loads, where row
count has no stable baseline. Avoid reading it on tables whose timestamp column records an upstream event rather than arrival (an
order placed last week and loaded today looks a week stale), and pair it with Row Count: a fresh table can still be half empty.

% ---------- Schema Changes ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Schema Changes}\label{sec:schema-changes}
\subsection{Columns and Types}

An upstream team renames a column, adds a discount field and switches a price from decimal to float. Nothing fails; downstream
queries silently read nulls or rounded cents. The schema monitor compares the full table definition at each scan with the one before
and flags every difference.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \Delta_t = {\color{nmlcyan}S_t} \,\triangle\, {\color{nmlpurple}S_{t-1}}, \qquad \text{anomaly} \iff \Delta_t \neq \varnothing
                $
            }
        };
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(-1.6,-0.2)$) to[bend right=15] node[pos=1, left] {columns and types now} +(-0.6,.5);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.south)+(-0.4,0.25)$) to[bend left=15] node[pos=1, left] {at the previous scan} +(-0.8,-.5);
    }
\end{center}

The symmetric difference $\triangle$ holds the columns added, removed or retyped; there is no expected range, since any change is an
anomaly by definition. A rename appears as one removal plus one addition.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_schema.png}
\end{center}

\textbf{Figure. Schema Changes.} \underline{Left:} the column count is flat for $33$ scans and steps from $6$ to $7$ at scan $34$.
\underline{Right:} the diff behind the step: a column added and a type changed. The count alone would have missed a type change on its
own, which is why the monitor stores the whole definition and not a summary.

\textbf{When to use it?}

On every table that other people's code reads, and on every table you do not control. Its alerts are rarely noise: something changed,
and every consumer must decide whether it matters. Avoid relying on it for semantic changes that leave the
definition intact (a currency switch inside a numeric column, an enum gaining a value); those show up in Average, Max or Unique Count.

% ---------- Missing Values ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Missing Values}\label{sec:missing-values}
\subsection{Completeness}

A field that is usually empty for $2\%$ of rows and is suddenly empty for $40\%$ has not failed any type check. Missing values
percentage tracks the share of null values in a column per partition, so a jump signals an upstream field that stopped arriving long
before anyone notices the blank segments in a report.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \text{missing}\%_t = 100 \cdot \left( 1 - \frac{{\color{nmlcyan}\text{count}(c)}}{{\color{nmlred}\text{count}(*)}} \right)
                $
            }
        };
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(2.2,-0.2)$) to[bend left=15] node[pos=1, right] {non-null values in the column} +(0.6,.5);
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(2.2,0.25)$) to[bend right=15] node[pos=1, right] {rows in the partition} +(0.6,-.5);
    }
\end{center}

SQL's $\text{count}(c)$ skips nulls, so the ratio is the share of filled rows and one minus it the share of empty ones. Empty
strings and sentinel values such as \texttt{N/A} or $-1$ are not null, so they count as present; catching them is a job for Unique Count
and for Min and Max.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_missing.png}
\end{center}

\textbf{Figure. Missing Values.} The country column is empty for about $2\%$ of orders every day, the band around it is a fraction of a
point wide, and the day an upstream field was renamed it jumps to $41\%$. The hollow marker is the day with no load: there is no
partition to measure, so the scan is recorded as missing rather than as a value.

\textbf{When to use it?}

On columns that downstream joins, filters and features depend on; a jump in missing values is the most common way a broken upstream
mapping announces itself. Avoid reading a stable non-zero level as a problem (many fields are legitimately optional) and remember that
the metric is blind to placeholders: a column that switches from null to \texttt{"unknown"} looks fully complete.

% ---------- Duplicates ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Duplicates}\label{sec:duplicates}
\subsection{Uniqueness}

A retrying job inserts the same batch twice and every total downstream is inflated by a few percent, too little for the row count to
notice. Duplicate percentage is the share of non-null values in a column that occur more than once, measured on the column that should
identify a row.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \text{dup}\%_t = 100 \cdot \frac{1}{{\color{nmlred}|R|}} \sum_{r \in R} \mathds{1}\big[\, {\color{nmlred}n(v_r)} > 1 \,\big]
                $
            }
        };
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(-0.4,0.3)$) to[bend left=15] node[pos=1, left] {records with a non-null value} +(-0.8,-.5);
        \draw[overlay,-latex,nmlred, semithick] ($(a.north)+(1.6,-0.2)$) to[bend left=15] node[pos=1, right] {how often record $r$'s value occurs} +(0.6,.5);
    }
\end{center}

Every copy counts, including the first: the values $[1, 1, 2, \text{null}, \text{null}]$ give two of three non-null records, $66\%$. On
a key column the expected level is exactly zero, so the band is as narrow as the floor allows and a single repeated batch is caught.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_duplicates.png}
\end{center}

\textbf{Figure. Duplicates.} The order id is unique on every ordinary day. On the day $6\%$ of rows were inserted twice, $2 \times 6$ of
every $106$ records share their id with another, $11.3\%$, and the monitor flags it while the row count on the same day stays inside its
band.

\textbf{When to use it?}

On primary keys and business keys, where any value above zero is a defect, and on columns that should be nearly unique (emails, device
ids) to catch a stalled id generator. Avoid it on categorical columns, where duplication is the normal state and the percentage sits
near $100\%$; a change in the number of categories is a job for Unique Count.

% ---------- Unique Count ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Unique Count}\label{sec:unique-count}
\subsection{Cardinality}

A customer id truncated to three digits by a type change still passes every null and duplicate check on an orders table: ids repeat
across orders anyway. What collapses is the number of distinct customers per day, from thousands to at most a thousand. Unique count is
the number of distinct non-null values in a column per partition.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \text{unique}_t = \big|\, \{\, {\color{nmlcyan}c(r)} : r \in P_t,\; c(r) \neq \text{null} \,\} \,\big|
                $
            }
        };
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(-0.5,-0.2)$) to[bend right=15] node[pos=1, left] {value of the column in row $r$} +(-0.6,.5);
    }
\end{center}

Its companion, count, is the number of non-null values; the two together separate ``fewer rows'' from ``fewer kinds''. Cardinality
scales with volume, so a half-empty partition also shows fewer distinct values, and the expected range must be read with Row Count
beside it.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_unique_count.png}
\end{center}

\textbf{Figure. Unique Count.} About $4{,}400$ distinct customers order on a weekday and $2{,}800$ at the weekend. The day ids were
truncated to three digits the count drops to $995$ of the $1{,}000$ values three digits allow. The partial-load day is flagged too: half
the rows bring fewer distinct customers, an anomaly that Row Count already explains.

\textbf{When to use it?}

On identifiers and on categorical columns whose set of values should be stable: a drop signals truncation, a broken join or a
defaulted field, a rise a new category, a change of case or a stray whitespace variant. Avoid it on free-text and high-precision
numeric columns, where nearly every value is distinct and the count just mirrors the row count.

% ---------- Average ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Average}\label{sec:average}
\subsection{Mean}

When $5\%$ of one day's amounts arrive in cents instead of currency units, the daily mean order value goes from $44$ to $252$.
The average is the cheapest distribution monitor: one number per partition that moves whenever the values themselves change, even when
their count, completeness and uniqueness are perfect.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \bar{x}_t = \frac{1}{{\color{nmlred}n_t}} \sum_{r \in P_t} {\color{nmlcyan}x(r)}
                $
            }
        };
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(-0.8,0.2)$) to[bend left=15] node[pos=1, left] {non-null values in the partition} +(-0.6,-.5);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(1.4,-0.2)$) to[bend left=15] node[pos=1, right] {numeric value in row $r$} +(0.6,.5);
    }
\end{center}

Missing values are ignored, the data is not sampled, and the mean reacts to every part of the distribution at once: a few extreme values,
a shift in the bulk and a change in a subset all move it, which makes it sensitive and, on its own, ambiguous.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_average.png}
\end{center}

\textbf{Figure. Average.} The same monitor catches three different incidents. The currency slip multiplies the mean by six and leaves
the frame. Refunds booked as negative amounts pull it down $6\%$, and a half-price promotion on cheap items $9\%$; both are outside a
band that normally allows about $3\%$. Which of the three happened is not readable from this page; Quartiles and Min and Max tell them
apart.

\textbf{When to use it?}

As the default monitor on every numeric measure that feeds a total or a KPI: price, quantity, duration, score. Avoid trusting it to
localize a change (pair it with Quartiles and Standard Deviation) and on heavy-tailed columns, where a single legitimate large value
moves it enough to alert; the median is the steadier choice there.

% ---------- Sum ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Sum}\label{sec:sum}
\subsection{Total}

Revenue reports read a total, not a mean. The sum per partition is the figure the business will see, and it moves for two unrelated
reasons: the values changed, or the number of rows did. It is the monitor closest to the number that matters and the hardest to
interpret alone.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \Sigma_t = \sum_{r \in P_t} {\color{nmlcyan}x(r)} = {\color{nmlred}n_t} \cdot {\color{nmlpurple}\bar{x}_t}
                $
            }
        };
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(-0.2,-0.2)$) to[bend right=15] node[pos=1, left] {numeric value in row $r$} +(-0.8,.5);
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(1.4,0.3)$) to[bend left=15] node[pos=1, left] {rows} +(-0.4,-.5);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.north)+(2.2,-0.2)$) to[bend left=15] node[pos=1, right] {mean} +(0.6,.5);
    }
\end{center}

The identity on the right is the diagnostic: a sum anomaly with a normal row count is a value problem, a sum anomaly with a normal mean is
a volume problem. Nulls contribute nothing, so a completeness failure also lowers the total.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_sum.png}
\end{center}

\textbf{Figure. Sum.} Daily revenue. The currency slip lifts it sixfold, off the scale, with the row count unchanged; the partial load
cuts it in half with the mean unchanged. The half-price promotion, which moved the mean by $9\%$, disappears here inside the volume
noise of a normal Friday: the sum's band inherits the noise of the row count and of the mean at once.

\textbf{When to use it?}

On the one or two columns whose totals appear in reports, so the monitor watches the same number the business does. Avoid using it as
a substitute for Row Count and Average: its band inherits the noise of both, so it misses moderate changes in either, and every alert
needs one of them to explain it.

% ---------- Standard Deviation ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Standard Deviation}\label{sec:standard-deviation}
\subsection{Spread}

Two days can share a mean order value and look nothing alike: one with every order near $44$, one with half at $20$ and half at $70$.
The standard deviation per partition tracks the spread of a numeric column, and it is the monitor that reacts hardest to a handful of
extreme values.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                s_t = \sqrt{ \frac{1}{{\color{nmlred}n_t} - 1} \sum_{r \in P_t} \big( {\color{nmlcyan}x(r)} - {\color{nmlpurple}\bar{x}_t} \big)^2 }
                $
            }
        };
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(-0.9,0.3)$) to[bend left=15] node[pos=1, left] {non-null values} +(-0.6,-.5);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(1.0,-0.2)$) to[bend right=15] node[pos=1, left] {value in row $r$} +(-0.8,.5);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.north)+(2.3,-0.2)$) to[bend left=15] node[pos=1, right] {partition mean} +(0.6,.5);
    }
\end{center}

Variance is its square and moves the same way. Because deviations are squared, one value a hundred times too large dominates the sum:
the standard deviation is the amplifier of the outlier, useful as a detector and useless as a description of the typical row.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_stddev.png}
\end{center}

\textbf{Figure. Standard Deviation.} Five percent of amounts in cents multiply the spread by forty, far more than they multiply the
mean, and send it off the scale. The refund day and the promotion day are flagged too, at $+15\%$ and $+11\%$: negative amounts and
halved prices both widen the distribution without moving its center much.

\textbf{When to use it?}

Beside Average on any numeric column, to tell a shift of the whole distribution (mean moves, spread does not) from a change in its
shape or tails (spread moves). Avoid it as a standalone alarm on heavy-tailed data, where it fires on every legitimately large order;
there, watch Quartiles for the bulk and Max for the tail.

% ---------- Min / Max ----------
\clearpage
\thispagestyle{observabilitystyle}
\section{Min and Max}\label{sec:min-and-max}
\subsection{Range}

A negative order amount, a delivery date in $1970$, a quantity of $9{,}999$: the values that break a downstream calculation are usually
the extreme ones, and a single row is enough. Minimum and maximum per partition watch the two ends of a column's range, which the mean and
the quartiles smooth away.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \min_t = \min_{r \in P_t} {\color{nmlcyan}x(r)}, \qquad \max_t = \max_{r \in P_t} {\color{nmlpurple}x(r)}
                $
            }
        };
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(-1.0,-0.2)$) to[bend right=15] node[pos=1, left] {smallest non-null value} +(-0.6,.5);
        \draw[overlay,-latex,nmlpurple, semithick] ($(a.north)+(2.6,-0.2)$) to[bend left=15] node[pos=1, right] {largest non-null value} +(0.4,.5);
    }
\end{center}

Each is a single value rather than an aggregate, so the expected range has to absorb whatever the most extreme legitimate row of the
day looks like; for the maximum of a heavy-tailed column that is a wide band and the occasional false alarm.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_min_max.png}
\end{center}

\textbf{Figure. Min and Max.} \underline{Left:} the minimum amount sits near $4$ until refunds are booked as negative orders, $-121$, and
again when a promotion halves the cheapest prices. \underline{Right:} the maximum jumps from about $330$ to $22{,}410$ on the currency-slip
day, off the scale, and is also flagged on a day whose largest order, $487$, was merely large: a single value is a noisy statistic.

\textbf{When to use it?}

On columns with a physical or business range (amounts, ages, percentages, dates) to catch sign errors, sentinel values and unit
changes; a fixed valid range can be set alongside the learned one. Avoid reading every Max alert as an incident on heavy-tailed
columns, and use Quartiles when the question is about the bulk of the data rather than its edge.

\clearpage
\thispagestyle{observabilitystyle}
\section{Quartiles}\label{sec:quartiles}
\subsection{Q1, Median, Q3}

Where the mean answers ``how much on average'', the quartiles answer ``how much for the typical row, the cheap quarter and the expensive
quarter''. The first quartile, median and third quartile per partition describe the shape of a column's distribution and barely react
to a few extreme values.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                Q_{{\color{nmlyellow}p}}(t) = \inf \big\{\, x : {\color{nmlcyan}F_t}(x) \geq {\color{nmlyellow}p} \,\big\}, \qquad p \in \{0.25, 0.5, 0.75\}
                $
            }
        };
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(0.0,-0.2)$) to[bend right=15] node[pos=1, left] {share of values at or below $x$} +(-0.6,.5);
        \draw[overlay,-latex,nmlyellow, semithick] ($(a.north)+(1.3,-0.2)$) to[bend left=15] node[pos=1, right] {the quantile level} +(0.8,.5);
    }
\end{center}

A quartile moves only when values cross it. Multiplying $5\%$ of the amounts by $100$ pushes those rows above every quartile, so each
quartile climbs to the value $5\%$ of the way further up the distribution, a shift of a few percent, while the mean multiplies by six.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_quartiles.png}
\end{center}

\textbf{Figure. Quartiles.} Q1, median and Q3 of the daily amounts, with the mean dashed. On the currency-slip day the mean leaves the
frame; Q3 rises $6\%$ and is flagged, the median barely moves. On the promotion day the picture inverts: Q1 drops from $25$ to $12$
because every price under $30$ was halved, while the median and Q3, which sit above the affected items, do not move at all.

\textbf{When to use it?}

On numeric columns where the question is how the bulk of the data is distributed, and wherever the mean is too jumpy: prices, durations,
latencies, anything heavy-tailed. Avoid them as the only monitor on the tails, since by construction they ignore the extreme values
that Min and Max exist to catch.

\clearpage
\thispagestyle{observabilitystyle}
\section{Text Length}\label{sec:text-length}
\subsection{Format}

Phone numbers that lose their country prefix, postcodes that gain a space, product codes that switch from twelve to fourteen characters:
format changes in text columns leave no null and no duplicate behind. The average, minimum and maximum character length per partition
are the cheapest proxies for format, and a shift in any of them says the strings changed shape.

% equation
\begin{center}
    \tikz{
        \node[inner sep=2pt, font=\Large] (a) {
            {
                $\displaystyle
                \overline{\ell}_t = \frac{1}{{\color{nmlred}n_t}} \sum_{r \in P_t} {\color{nmlcyan}\text{len}}\big(s(r)\big)
                $
            }
        };
        \draw[overlay,-latex,nmlred, semithick] ($(a.south)+(-0.8,0.2)$) to[bend left=15] node[pos=1, left] {non-null strings} +(-0.6,-.5);
        \draw[overlay,-latex,nmlcyan, semithick] ($(a.north)+(1.2,-0.2)$) to[bend left=15] node[pos=1, right] {characters in the string} +(0.6,.5);
    }
\end{center}

Minimum and maximum length bound the format: a fixed-width code should have all three equal, and a minimum of zero means empty strings
are arriving in place of nulls, which Missing Values would not have seen.

\begin{center}
    \includegraphics[width=\textwidth]{figures/Observability_text_length.png}
\end{center}

\textbf{Figure. Text Length.} Every phone number is eleven characters long, so the band is as narrow as the detector's floor allows. The
day $60\%$ of numbers arrived as seven-digit strings, without the formatted prefix, the mean length fell to $8.7$: no value was missing,
none was duplicated, and every row still passed the column's type.

\textbf{When to use it?}

On identifiers, codes and any text field with a de facto format that downstream parsing relies on: phone numbers, postcodes, SKUs,
email addresses. Avoid it on free text (comments, descriptions), where length varies too much for the band to mean anything, and use
Unique Count there instead to catch a column that suddenly carries the same placeholder.
